# Spec 0025 — Selected-output configuration guards: design

## Owned files

`code/main.py` argument validation/publication entry, `code/tools/finalize_run.py:checked_candidate_files`, existing
publication/packaging tests and `code/README.md`.

1. Determine whether args.out resolves to the repository's selected output. If so, validate release configuration
   immediately after argument parsing, before loading data/providers or deriving a run's files.
2. Require --cases all, no --case option, no ablation, ungrounded-account-steps=none, online/default mode, and the
   canonical dataset root. Explain the rejected mode and direct diagnostic runs to an alternate --out.
3. Keep destination policy separate from mode support: offline/sample/custom/ablation runs remain usable in scratch
   paths. A scratch directory's output.csv is not the selected file. Use normal Path resolution instead of suffix
   matching or OS-specific string rules.
4. Make the finalizer's declared-mode check explicit for --cases sample and selectors (including an explicitly empty
   selector). Continue validating against the actual release request set. A portable candidate's original absolute
   data_root string is not by itself a dataset identity proof; do not add a machine-path equality check at finalization.
5. Reuse the existing checks for offline/ablation/ranked candidates. Share common predicates after actual duplication,
   keeping CLI destination-only requirements out of an unrelated generic validator.
6. Extend test_run_publication.py. Point SELECTED_OUTPUT/REPO_ROOT to an isolated fixture and assert a generation spy
   was never called on refusal. Verify old bytes and diagnostics/manifest survive each refusal. Keep positive tests
   for alternate destinations and default full publication with fake providers and honest synthetic provenance.

## Baseline reachability reproduction

With the default --out, the actual parser and guard permit:

```text
--cases sample --offline
--ablate trust-claims --offline
--ungrounded-account-steps ranked --offline
```

They refuse `--case case_01 --offline`. The reviewer exercised only argument parsing/the guard; no selected file
was overwritten. Read main.py's validation/publication path to reproduce the end-to-end failure safely in a fixture.

## Release after implementation

Complete the offline tests and bounded sample comparisons first. The preserved b90914b output is still known to have
the temporal defect; do not relabel it as generated by 0022–0025. A new live sample/evaluation/full-run configuration
requires explicit permission. On permission, freeze and publish producing code, capture matching evaluation inputs,
generate a separate candidate, validate and finalize the matching bundle, then rebuild/package and verify it. Without
permission or reusable complete caches, report release regeneration blocked; do not invent metrics or select an offline
ablation as the default submission.
